## 研究问题

在相同求解环境和模型预算下，启用命令策略 v3，能否减少明确越界操作，同时不损害修复结果？

- A 组：`command-policy=off`，正常执行模型工具调用。
- B 组：`command-policy=enforce`，拒绝已明确识别的违规请求；unknown 仍执行。
- 两组均使用 `swebench-isolation-v2`、同一实现、镜像和依赖，均开启轮数提醒、关闭显式 finish。不复用旧环境下的基线成绩。
- 不同时加入结构化工具、检索、上下文压缩或 thinking 消融，避免无法解释差异。

## 准备与冻结门槛

1. 按候选题逐个准备镜像，构建并发先用 1；记录实际 image ID、架构及任务定义版本。不以可变的 `latest` 标签作为最终身份。
2. 每题通过 v2 隔离预检，以及一个不依赖标准答案的可见健康检查。预检必须覆盖导入位置、缓存遮蔽、Git 隔离及判卷材料检查；不把旧三题的验收视为新题已通过。
3. 在独立验证容器中完成 gold 官方判卷，并确认未修复基线确实能复现目标失败、测试正常收集。gold 和测试补丁只供验证使用，不能留在求解镜像或回填模型。
4. 当前 harness 的批量 CLI 会跳过空补丁，不能把“提交空预测得到 unresolved”当作执行了基线测试。新验收桥直接调用官方 `run_instance(skip_patch=True)` 跑未修复基线，不伪造补丁；必须有真实日志、非零测试退出码和至少一项目标 F2P 的 FAILED 状态，缺失、跳过或 ERROR 均不算复现。
5. 核对模型计费与预算，准备带默认 dry-run、输入哈希检查及新 run-id 保护的启动器。运行前必须补齐后文的官方判卷完整性检查和异常用量恢复，验证缺报告、判卷异常、API 中断及费用未知等错误路径。
6. 所有题目通过后，另建最终执行配置并在首个模型请求前提交：固定题号、完整数据记录哈希、镜像 ID、实现／启动器／依赖哈希、环境与命令策略、判卷工具和任务仓库版本。

六题的本地任务定义目录均存在。首题镜像已构建，独立基线规范化通过，完整预检被目标 Python 2.7 阻断；其余五题镜像尚未准备，六题均无官方 baseline／gold 验收结果。主机可用空间约 142 GiB 是创建草案时的快照，不等于镜像容量承诺。后续按实际 Docker 磁盘增长逐题构建，不自动清理其他项目。

只有在首个模型运行前，遇到有证据的构建、依赖、环境隔离或判卷基线问题，才允许替换候选：沿草案中同仓库、同难度的排序选择下一题，保留原候选及失败原因，重算题单和数据哈希。该层耗尽则暂停重新评审，不跨层随意补题。开始模型对照后，不因失败、费用或没有策略命中而换题。

## 配对与执行顺序

每个“题目 × 重复编号”构成一对，相邻执行 off 和 enforce，共 18 对、36 个独立 run-id，准确顺序见草案的 `pairs`。

- 每遍六对，其中三对 off 先运行，三对 enforce 先运行；三遍合计各 9 对先手。
- 每遍轮换题目起点，单题跨遍交换先手，不宣称奇数遍能让每一题的先手次数完全相同。
- 每次使用新容器，同题两组不共享工作目录、补丁、轨迹、测试反馈或判卷结果。
- 后续启动器按一遍或一对显式启动，不默认运行全部 36 次。启动前先 dry-run，真实模型仍由人工发起。

总计最多 1,440 次 Agent 轮次；SDK 重试可能增加实际 HTTP 请求。中断先核对已保存的预测、结果、轨迹与配置，不删除后挑最好一次。环境或判卷异常暂停继续，不标为模型解题失败，也不从正式题单静默删除；基础设施修复后只在相同补丁上补判，若必须重新求解则先修订计划并保留原尝试。

批量入口已改为对不可变预测快照判卷，逐次使用唯一 ID，保存原件／快照哈希、harness 退出码、汇总、逐题报告及日志。缺报告、非零进程退出、明确基础设施错误、空测试集合或缺测试日志保留 `resolved=null`、`grading_status=error`，不再回退为普通 false。真实空补丁仍按未解决处理，不要求不存在的测试日志。

`no_tests_collected` 等模糊标签及测试自身输出不直接覆盖官方结论；只有与报告矛盾的零收集证据、缺失数据或明确环境故障才阻断，模糊分类留档。完整解决率必须覆盖计划分母，预测已保存但结果缺失时保持未知。普通需要复核的 `agent eval` 返回 2；人工 Ctrl-C 保持常规退出 130，已收到的结果和部分 summary 先保存。未来 A/B 启动器必须据此停止下一对，而不是只检查是否产生了文件。

## 指标与判读

**主指标**是官方 resolved。每组计划分母为 18 次求解，始终同时写明只有 6 道不同题；模型请求错误、耗尽预算、空补丁和正常判卷未解决均保留。基础设施未完成时展示已完成／计划数量和原因，不用较小分母报完整解决率。

按题目分别列出 off 与 enforce 在三遍中的成功数及差值，并列出 18 对原始结果。重复尝试和同仓库题目相关，不能把 36 次求解当作 36 个独立样本来宣称显著提分；本先导实验以描述性配对结果为主。

辅助指标包括模型轮次、prompt／cached／completion tokens、费用估算、空补丁、停止原因、命令分类及实际拦截。默认 off 没有在线判定事件，不能拿它的零计数与 enforce 的拦截数作行为改善对比；必须用同版分类器对 off 的保存轨迹离线分类，并与 enforce 事件核对。

费用和轮数统计覆盖全部尝试，不只统计成功题。已在响应解包、工具执行之前保存可用用量；异常时从轨迹逐轮 usage 与终态交叉核对恢复，不重复相加。`turns` 是已记录响应轮次，`model_calls_attempted` 包含失败的模型调用尝试，`http_attempts` 是观测到的传输次数，三者不混算。

线程隔离的 HTTP 请求观察记录 SDK 重试；成功重试也可能有未报告用量的请求。缺字段、轨迹不完整、计数矛盾、执行异常或未报告 HTTP 尝试时，`cost`／批次 `cost_cny` 保持 null；`known_cost`／`known_cost_cny` 仅表示用项目价表对已记录 token 的估算，不是实际账单或可靠下界。单次直出在应用补丁前保存用量，响应解析失败和中断也不再自动写成免费调用。

服务商账单与本地估算分别保留，不能仅用估算断言已省钱。上述代码保护不等于硬费用熔断，也不代替模型预算确认；六题环境、完整冻结配置和 A/B 启动器仍未就绪，不能直接开始模型运行。

逐条复核 enforce 的拒绝请求和后续行为，区分明确越界、正常工作受阻和无法判断。不把未知请求算作覆盖，不把一次拒绝等同于节省一轮或提高成功率。首次编辑轮次需要工作区变更证据，当前轨迹未完整记录逐命令快照，暂不作为可直接自动汇总的指标。

如果各题结果大致持平而正常操作被误拦，优先保留默认 off；即使本轮结果更好，也先整理逐题证据及不确定性，再讨论扩大新题范围或修改默认值。不能依据部分结果临时改规则并继续沿用同一个实验名称；修订策略需另建对照。

## 预算依据

仅使用已归档的 DeepSeek 提醒组三遍、9 次求解作历史测算：估算费用合计 ¥0.6550，单次均值 ¥0.07278，样本最高 ¥0.12077。按相同旧计价口径，36 次乘均值约 ¥2.62；全部按样本最高单次估算约 ¥4.35。来源路径保存在草案中。

这些数字不是当前服务商报价，也不是新题费用上下界。`llm.py` 的历史价格表、缓存命中、服务时段、输出长度和超时重试均可能改变实际账单；运行前应以服务商控制台核对费率及余额。

建议把 **¥10 作为待确认的人工复核阈值**，不是已经批准的额度，也不是已实现的自动硬限额。阈值检查应在配对之间进行，单对内仍可能超出预计；没有费用硬熔断时，不能承诺最多花 ¥10。未确认价格口径与预算前不启动模型。GLM 不加入本轮，避免同时扩大变量和成本。

## 使用准备入口

在项目根目录默认只检查本地缓存、配置和镜像，不初始化模型、不建容器，不下载数据或镜像：

```bash
uv run python evals/profiles/command-policy-ab6/prepare.py
```

缺图时输出 `check_only`、`ready_for_model_run=false` 并返回 2，这是未满足前提，不是模型实验失败。先在 harness 工作目录按单题、并发 1 构建第一题：

准备入口同时识别数据集标签和本地构建器的 `sweb.eval.x86_64.<instance_id>:latest` 标签，记录实际匹配名称并固定 image ID，不重新打标签或复制镜像。若已存在的候选标签指向不同 image ID，必须先显式处理冲突，不能静默挑一个。

```bash
cd ~/code/swebench-work
caffeinate -i swebench images build ./swe-bench-tasks \
  -i psf__requests-1724 -j 1
```

构建会下载镜像层及依赖，由人工发起，本轮开发没有执行。构建完成后回到 patchloop 项目根目录，在全新私有目录中显式执行一次无模型验收：

```bash
caffeinate -i uv run python evals/profiles/command-policy-ab6/prepare.py \
  --execute --instance psf__requests-1724 \
  --artifacts /tmp/patchloop-ab6-preflight/requests-1724-r1
```

默认可见健康命令仅为 `python -m pytest --version`，确认 pytest 可启动，不作为修复成功证据。随后分别检查 v2 求解环境，以及固定原始镜像上的 baseline／gold 官方测试；控制容器使用无网络、2 CPU、3GB、移除 capabilities 和禁止提权，但**没有 solver 的缓存遮蔽及 Git 裁剪**。两轨通过不等于完整隐藏测试套件已经在 v2 隔离环境执行通过。

本地构建器可能在任务基线上追加权限整理提交。为此，raw 检查和两条控制轨在各自的一次性容器中先验证指定基线的祖先关系、路径／对象类型／blob 内容以及已跟踪工作区和索引；只有内容不变的普通文件 executable 位变化或空提交允许规范化。核验通过才恢复准确 base commit，随后核对 HEAD、tree 和干净状态；源码修改、增删文件、隐藏索引修改均不能通过 reset 被掩盖。gold 补丁在规范化之后应用，不能先应用再被重置。

规范化前后提交、tree、权限变化数量和 helper 哈希写入证据，并与隔离后 solver 的 HEAD/tree 比较；原始镜像保持不变。此兼容处理不更改 v2 缓存与材料隔离规则，也不把构建器提交直接当成任务基线。

2026-10-19 首题实际检查：`requests-1724` 的本地镜像已构建，标签映射和独立基线规范化通过，但完整预检被 Python 2.7.18 与现有 v2 Python 3 探针不兼容阻断，未进入官方 baseline／gold。见[首题检查记录](../../reports/command-policy-ab6-preflight/README.md)。不能通过改用另一解释器导入目标项目来冒充原运行环境通过；是否兼容旧解释器或按已保存排序替换候选另行决定。本轮不修改六题候选、排序、分母及模型授权。

桥接层只支持已经核对的 swebench 5.0.2；版本或接口变化、带额外 image assets、缺图、身份不符、测试证据不足或清理失败均拒绝验收，不自动拉取、构建或删除镜像。可以用 `--harness-python` 指定已安装 harness 的虚拟环境 Python，保留其 venv 路径。

产物根目录使用 0700 权限，完整输入单独以 0600 保存，控制进程不继承模型／GitHub 凭据。目录中的原始日志和 gold 材料仅供验证，不进入求解容器或 Git；入口拒绝写到项目源码区，只允许外部目录或被忽略的 `data/`。`result.json` 保存身份、输入和产物哈希，失败也保留证据，已有目录拒绝覆盖。
