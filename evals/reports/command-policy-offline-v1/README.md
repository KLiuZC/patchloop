## 结论

固定十遍 xarray 三题轨迹包含 985 条 bash 请求。689 条允许，95 条拟拦截，201 条未知；明确分类范围为 79.6%。逐条检查 95 条拟拦截请求后，66 条包含明确的范围外操作，29 条属于有限 Git 历史查询，有限制过严的风险。

**暂不启动新题 enforce 模型实验。** 先明确有限 Git 元数据查询的允许范围，保留全历史搜索、内容搜索、reflog 和对象恢复限制。修改时另存策略版本及新的离线结果，不能覆盖本报告。未知命令继续保留，不以一律拒绝 Python、命令替换或清理操作来提高表面覆盖率。

本次没有证明策略提高解决率、节省轮数或降低费用。模型收到拒绝反馈后会改变后续行动，不能从旧轨迹直接模拟新结果。

## 拟拦截复核

95 次请求对应 88 种不同命令／规则组合，全部逐条核对，记录见 [review.json](review.json)。

| 复核分类 | 次数 | 解释 |
| --- | ---: | --- |
| intended_block | 66 | 包下载、仓库外递归搜索、额外版本源码或全历史／恢复查询，符合本阶段限制范围 |
| scope_tradeoff | 29 | `git log --oneline -3/-5/-8` 等有限查询，规则虽命中但可能干扰正常诊断 |

例如，`git log --oneline -5 && sed -n '600,700p' xarray/core/variable.py` 会整条被拒绝，连正常文件读取也不会执行。旧环境只剩一个基线提交，此类查询本身未提供其他提交；这类交互成本不能当作节省轮数的收益。29 次占拟拦截请求的 30.5%，不是已测得的总体误拦截率。

在已复核的拟拦截集合中，未发现明确违反既定 v1 规则的解析误判；但这不等于“零误拦截”。本次没有为全部正常操作建立独立真值，规则本身也可能过严。不能计算总体准确率、误拦率或漏拦率，不能把合乎规则的阻断一律解释成必要阻断。复核不是独立盲审，也不判断模型的真实意图。

禁止规则命中次数分别为：历史搜索 47、仓库外搜索 41、下载／安装 12、额外项目源码 3。一条请求可以同时命中多个规则，因此这些数字不能相加作为拟拦截请求总数。

## 未知命令

201 条 unknown 的规则组合如下：

| 原因组合 | 次数 |
| --- | ---: |
| 仅 opaque_script | 176 |
| 仅 unsupported_command | 12 |
| 仅 dynamic_shell | 8 |
| dynamic_shell + unresolved_path | 2 |
| dynamic_shell + unsupported_command | 1 |
| 仅 unparsed_shell | 1 |
| opaque_script + unsupported_command | 1 |

对不是“仅 opaque_script”的 25 次请求逐条复核，包括：

- 用 `$(grep …)` 定位当前仓库的函数行号，随后执行 sed 读取。
- 用 awk、sort、diff 对照测试输出，以及清理 `/tmp` 下的临时目录。
- 查询当前提交的时间、缓存列表或 Git 元数据；有些仍属于继续探查额外信息的尝试，但没有足够独立标注据此计算漏拦率。
- 一条带嵌入 Python 和反引号的命令未被完整解析；原工具输出也包含 shell 错误。离线检查不执行或修补它。

176 条仅因脚本不透明而未知的请求没有逐条做真实意图标注，其中包含正常 Python 编辑和复现操作。后续若希望提高可解释性，可优先支持安全明确的输出处理形式，或另做结构化编辑工具；不把所有未知请求改成拒绝。

在保留完整本地轨迹的工作区，可输出到一个新文件复算：

```bash

  --output /tmp/patchloop-command-policy-offline-recheck.json
```

这不是 `agent eval --command-policy audit`，不会请求模型或执行工具。输出文件已存在时拒绝覆盖，也不允许输出到源 `evals/results` 内。完整轨迹仍按原约定不入 Git；只克隆公开仓库可以阅读本报告，但缺少轨迹时不能重新分类，脚本会明确失败。
