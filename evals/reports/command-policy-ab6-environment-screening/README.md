## 两类新增风险

### Sphinx：构建阶段会尝试修改仓库文件

`10449` 的配方包含 `sed -i 's/pytest/pytest -rA/' tox.ini`。`9673` 除同一命令外，还调整 `setup.py` 中的 Jinja2、sphinxcontrib、alabaster 和 markupsafe 约束。这些命令位于安装依赖之前，构建末尾的提交会包含实际产生的已跟踪改动。

当前基线规范化仅接受内容不变的权限变化或空提交。**若这些命令实际改变文件内容，规范化会拒绝，不能把它们当成权限整理后直接 reset 掉。** 某条替换可能没有匹配，因此静态检查只能标记风险，不能声称已观察到这两题的镜像差异或运行失败。

原排序中 Sphinx 的 18 道候选都声明同一条 `tox.ini` 改写命令；逐个换题不能避开这项配方特征。本次不将 18 题批量判为不合格，也不宣称分层已耗尽，更不跨仓库补题。优先检查一题的实际文件差异并设计可核验的环境适配。

### Requests：非 editable 安装可能留下仓库外副本

7 道 Requests 候选均使用 `python -m pip install .`，而 8 道 pytest 候选均使用 `python -m pip install -e .`。前者通常在 site-packages 中生成项目副本；当前 v2 探针会检查 `/opt` 下的仓库外项目目录，固定缓存遮蔽目录不包含目标环境的 site-packages。

即使 `python` 从 `/testbed` 导入了正确版本，另一份可读取源码仍可能触发隔离门槛。**这不是已证实的新版本答案污染**：本次没有检查这些新镜像的实际副本及版本。后续需核对路径、内容和依赖关系，不能忽略扫描结果或直接删掉整个 site-packages。
