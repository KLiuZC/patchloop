# 4B 基线归档

归档日期：2026-09-30。SWE-bench Verified 固定 30 题，5 次运行共 150 次答题；所有原始结果保留，未根据模型成绩删题或人工补分。

## 阅读入口

- [结果表](results.md)：总分、费用、过程指标、失败类别、仓库和难度分层。
- [逐题表](instances.csv)：150 行，每行对应一次答题及其官方判卷计数。
- [结构化汇总](summary.json)：可供后续画图、对比实验读取。
- [判卷证据摘要](evidence.json)：官方汇总、逐题 F2P/P2P 计数、导入错误摘录及原日志哈希。
- [配置与校验信息](manifest.json)、[源码快照](source.zip)：供后续对比版本；快照仅包含源码、依赖锁和题单，不含凭据或模型推理内容。
- [两道 pylint 题的诊断](../../results/v30-glm/diagnosis.md)：保留原始成绩，单独解释测试依赖与目标行为分歧。

## 离线复算

在项目根目录运行，仅用 Python 标准库，不连接模型、不启动 Docker：

```bash
python3 evals/summarize_baseline.py
```

脚本先验证固定题单、原始摘要/答卷/结果、证据摘要和源码压缩包的 SHA-256，再校验五次运行均覆盖相同的 30 个题号，模型结果与官方解决题号一致，空补丁计数一致。然后生成 `results.md`、`summary.json`、`instances.csv`。不要编辑旧答卷来更改分数；未来实验使用新 run-id。

## 已完成的实验

| 配置 | run-id | 解决数 | 说明 |
| --- | --- | --- | --- |
| DeepSeek + agent | v30-deepseek-r1/r2/r3 | 20、19、20 / 30 | 同一题单重复三次，均值 65.6%，样本标准差 1.9 个百分点 |
| GLM + agent | v30-glm | 20/30 | 1 次 API 超时仍计在分母；只运行一遍 |
| DeepSeek 单次直出 | v30-single-shot | 4/30 | 23 份补丁未能应用、2 份输出截断、1 份有效补丁未通过目标测试 |

Agent 每题最多 40 次模型请求、工具命令超时 180 秒、两个任务并发、每容器 3GB；单次直出一个任务串行、没有工具。官方判卷并发数 1。API 未显式设置 temperature 或输出 token 上限，模型使用其默认行为。模型别名可能随服务商更新，不保证历史运行可逐字复现。

标准差仅表示这三次运行的波动，不是总体准确率的置信区间；90 次重复答题仍只有 30 个不同问题。单次直出同时失去了源码访问、工具执行和反馈，不构成“仅去掉循环”的单变量消融。

费用是内置价格表乘以已记录 token 得到的估算；DeepSeek 使用谷价表。`summary.json.seconds` 是每题耗时之和，两个任务并发时不是全程耗时。失败 API 请求的 token 可能未记录，不能以项目估算代替供应商账单。

## 判分与失败归因

- 空补丁、请求超时都计入 30 题分母；官方只为有有效补丁的任务生成逐题测试报告。因此单次直出“官方完成 5 题、解决 4 题”对应总成绩 4/30。
- `finished=true` 只代表模型不再发工具调用；可能未完成修复。40 轮上限统计不把 API 异常算进去。
- 空补丁只代表没有交出改动，不能自动判定“从未编辑过文件”或“在找答案”；行为原因需要读轨迹。
- DeepSeek 三遍的 31 次未解决包括：12 次空补丁、5 次测试导入受阻、14 次测试未满足判分标准。GLM 为 1 次 API 超时、1 次空补丁、2 次导入受阻、6 次测试未满足判分标准。
- pylint-4604：隐藏测试导入标准答案新增的 `IS_PYPY` 常量，GLM 未提供它；只补常量即可让原业务修法通过 21 个测试。诊断通过不能改写原答卷成绩。
- pylint-4661：隐藏测试需要 `appdirs`。GLM 补装此包后仍有路径断言失败：实际 `.local/share/pylint`，官方要求 `.cache/pylint`。题面有 data/cache 语境，记录为与官方验收预期不一致，不武断归因于模型智力。
- 还有测试输出与官方判分范围不同的情况：xarray-3993 的日志中有 pandas/xarray 版本检查错误等非判分目标失败，DeepSeek r2 仍被官方判为 resolved。官方 F2P/P2P 集合通过不等于整个测试模块全绿。
- 本次归档中官方 P2P 集合未记录失败，但每遍只有部分任务具备非空 P2P 结果（25/23/25/26/5 道）。不能声称全部原有测试无回归，更不能据此证明循环设计消除了回归。

## 当前复现能力的边界

题单固定为 6 个仓库各 5 道，难度 12/15/3，种子 20260929。gold 校验 30/30 通过，说明标准答案在该环境可判分；并不证明隐藏测试与特定修法无关，也不保证以后没有 API/环境异常。

归档源码取自当前工作区，包括既有的 `eval.py` 本地镜像复用修改；历史评测没有逐次记录源码哈希、数据集 revision、镜像 digest 和完整请求配置。因此这是**事后归档的基线快照**，不是五次运行都经过版本证明的历史镜像。`manifest.json` 明确区分了当前快照与从日志/启动命令恢复的配置。

原始模型轨迹仍在各运行的 `traj/`，按现有规则不进入 git；本归档可离线复算成绩与失败分类，但完整逐轮回放仍需要这些本地轨迹。评测输出与题单可以共享，模型 API 和已有 Docker 镜像仍是重新答题的外部条件。

## 下一项实验：仅增加剩余轮数提醒（待实施）

假设：让模型明确知道还有多少次请求机会，能减少空补丁或无效探索；可能无效或干扰正常解题，因此仍要测成功率。

实验预案：

1. 基线行为保持为默认，通过独立选项开启提醒。在请求第 21 轮前提醒“还剩 20 轮”，请求第 36 轮前提醒“还剩 5 轮”，计数包含即将发送的请求。以实际模型请求轮数计数，不把一次回复中的多条工具调用误算为多个轮次。
2. 提醒只告知预算并要求推进修复、验证和收尾，不提供任何题目答案；不同时增加 finish 工具、压缩上下文、改变工具集或限制搜索。
3. 新增提醒需进入轨迹记录；先通过假模型检查触发时机、默认关闭与工具消息顺序，再用 smoke5 验证完整闭环。
4. 运行前保存代码/提示词哈希、模型名、题单哈希、依赖版本、并发/超时/预算配置和开始结束时间。若提供输出上限，两个对照组应一致，不能只改实验组。
5. 开始付费对比前固定运行次数和 run-id：建议 DeepSeek 三遍，使用 `v30-budget-r1/r2/r3`；与本归档比较 resolve rate、空补丁数、达到上限数、费用与自行收尾数，不只挑最好的一遍。
6. 首次编辑轮次需要根据真实文件变化记录，不能只搜索命令里的 sed/python，也不能把“当前有 diff”当成“已修好”。这项观测应在控制组/实验组一致启用。
7. `verified30` 已被查看失败轨迹，并将影响改进设计，此后作为开发/对比集。最终结果另留未用于调参的题单；看完本集合后不能再将其称为完全未见的报告集。

本次归档未实现该机制、未发起新模型调用，也未改动当前 agent 的行为。
